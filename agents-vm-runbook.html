Agents VM · VMID 100 · technical runbook

Isolated Hermes agents, and the persistent knowledge layer underneath them

Four independent AI agents on one host, each with its own identity, credentials, and now its own long-term memory — enforced by filesystem and network boundaries, not by prompting. This page is the deep architectural reference; the Home Lab Runbook carries only this VM's summary card alongside the other three hosts.

Agent isolation model

The baseline every agent gets, independent of GBrain
current

Each Hermes container gets its own mode‑restricted bind mount at a <per-agent state path> — not readable by the host's own primary account — plus, for hermes‑1/hermes‑2, a read‑only view of a shared‑data directory (currently empty). hermes‑3 is the deliberate exception: read‑write access to that shared data, and its own Docker network, which is also the only network whisper‑ivrit joins — the seam that lets the household agent use shared speech‑to‑text without exposing it to the personal agents. hermes‑4 has neither the shared‑data mount nor any household network membership.

Named sub‑profiles (hermes‑2 runs three: coder, hercules, and sdr/“Sudri”, a Slack persona for a separate workspace; hermes‑1 and hermes‑4 each run a coder profile) are additional identities multiplexed inside the same container, each with its own state directory and no inheritance from the base profile's configuration — a fact that matters below, since the knowledge layer had to account for it.

GBrain + Obsidian knowledge layer

Persistent, long-term memory — additive to each agent's existing skills and instructions
current

Every agent also gets a persistent knowledge brain (GBrain) and an Obsidian‑compatible Markdown vault, layered on top of — and kept strictly separate from — each agent's pre-existing skills, instructions, and native short-term memory. Four distinct layers, deliberately not conflated:

Four brains, one deployment definition

Shared software, never a shared database
current

Why the split: GBrain's own trust model treats a local process as always fully trusted, full read+write, no exceptions — enforcement only exists for remote/HTTP callers with a scoped token. Originally the three personal brains ran as local processes since each had exactly one caller. That stopped being safe to rely on once each container's named sub‑profiles also needed the same personal brain: a single-writer embedded database can't have two independent local processes open at once, so all three were promoted to the same always‑on HTTP pattern the household brain used from day one — see “Concurrency” below.

How a message becomes a memory

The runtime path, not just the architecture
current

Two capture paths exist deliberately: capture is the explicit one (“remember this”, “save this thought”) for when the user directs it; signal-detector is the ambient one that runs regardless, so knowledge doesn't depend on remembering to ask the agent to remember. Both write through the same remember/put_page primitives, so retrieval doesn't need to know which path a fact came from.

Isolation holds during this whole path, not just at rest. A write always lands in the calling profile's own brain — there is no code path where a fact learned in hermes‑1 can be written to gbrain‑shaked, because hermes‑1 has no credential and no network route to it at all. Cross‑owner access fails the same way whether it's attempted mid‑conversation or from outside one entirely: a DNS resolution failure, not an authorization check that could be bypassed.

Sub-profile access policy

A same-owner decision, not a new privacy domain
current

Named sub‑profiles were deliberately left out of the original rollout, flagged as an open decision. That decision: a sub‑profile shares its parent identity's personal brain in full — not a separate brain, not read‑only, not excluded. coder on hermes‑1/2/4 is that owner using a different tool surface, not a different identity; hercules and sdr on hermes‑2 are likewise treated as Shaked, not as separate privacy domains, and read/write the same brain as Shaked's base profile. No sub‑profile has its own isolated brain, and none has ever been given access to a brain outside its own container's owner.

MCP wiring & secrets

HTTP everywhere now, one bearer token per owner
current

Every registration is HTTP, persisted per‑profile in that profile's own configuration (base profile and every named sub‑profile each hold a separate, non‑inheriting config file). One read,write‑scoped bearer token per owner — no read/write split needed, since every client of a personal brain is that owner in some interface — shared by every profile under that container. The household brain is the one case needing genuinely different scopes per caller, which is exactly what HTTP's scoped tokens are for and a local process's full‑trust model can't express.

Tokens are minted directly against each brain container, sops‑encrypted per agent, and merged into that container's runtime environment at deploy time — never committed in plaintext, never logged. Token values are not disclosed here; only the wiring shape is.

Why HTTP, not a locally spawned process

A single-writer database and what that forces

The brain's embedded database is single‑writer, single‑process: whichever process opens it first holds an exclusive lock for as long as it runs. A second independent process against the same data — even a brief admin command — fails on that lock rather than silently corrupting anything. That's a hard constraint, not a tuning knob, and it's the entire reason every brain with more than one legitimate concurrent caller runs as one always‑on HTTP service instead of a process spawned fresh per caller. It's also why routine maintenance (minting a token, a one‑off diagnostic command) briefly pauses that one brain's service rather than reaching into it while it's live — never two independent processes against the same data directory at once, regardless of transport.

Backup & restore

Nothing new to configure — covered by the whole-VM job
current

Every vault and every brain's data directory lives on the same VM disk already covered by the nightly Proxmox Backup Server job described in the Home Lab Runbook — nothing agent‑specific was added to that schedule. The vault Markdown is the one irreplaceable piece; the brain's own database/index is rebuildable from the vault by design (that's the point of treating Markdown as the system of record).

01
Restore VM100 from the whole-VM PBS job (see the Home Lab Runbook's restore steps — identical procedure, no agent-specific variant).
02
docker compose up -d from the repo checkout recreates every container, including all four brain services, from the restored data directories — no reindex normally needed.
03
If a brain's database directory alone is corrupt but its vault survived, that one brain can be reinitialized and resynced from its own vault — the database is a derived cache, not the source of truth.
04
Re‑run the isolation verification pattern above before resuming normal use.

Known failure modes

Gotchas already hit once — don't re-discover them
01
Two processes, one data directory, always fails. The embedded database is single‑writer. A second independent process (a diagnostic command, a duplicate registration) against a brain that's already live fails on the lock instead of silently corrupting anything — expected, not a bug. Fix: never run a second process against a live brain's data directory; use the one already running.
02
Named sub-profiles have their own configuration — no inheritance from the base profile. A fix applied to a container's base configuration does not reach its named sub‑profiles; each one needs the same change applied to its own separate config independently. This bit an earlier, unrelated speech‑to‑text fix before it bit the knowledge‑layer rollout — same root cause both times.
03
Don't manually poke an individual profile's gateway service after boot. On container start, the main multiplexed process and each named profile's own standalone service both race for that profile's platform token; the main process is expected to win and absorb it. Manually nudging the standalone service well after boot can instead let it win that race and knock the main process's session offline. Recovery is a plain container restart, not further service-level intervention.
