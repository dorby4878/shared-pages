Trust & network boundaries

Three paths, and the boundaries between them
current

These paths never cross: cloudflared cannot reach Komodo, Mongo, or any database directly, and nothing admin-facing is routed through the tunnel. This network model (dedicated per-app networks, Caddy joining each directly) applies to apps built under this design; the pre-existing Caddy, Komodo, and monitoring stacks predate it and were not migrated — that's why Komodo and Uptime Kuma still publish straight to the Tailscale IP instead of sitting behind a Caddy-fronted network of their own.

NOW — current public path

Expo web front-end + Socket.IO server
current

NOW is reachable from the internet through an outbound-only Cloudflare Tunnel, with Caddy as the only thing between the tunnel and the application. There is deliberately no Authentik and no router port-forward anywhere in this path:

Internet -> Cloudflare DNS/WAF -> Cloudflare Tunnel (outbound-only, no inbound port) -> Caddy route /socket.io/* -> now-server everything else -> now-web

Authentik protects trusted internal/management applications — it is not part of NOW's identity model and was deliberately removed from this route. NOW is a public end-user application; if it ever has its own authentication, that's independent of Authentik entirely.

Accepted risk, current: NOW has no application-level authentication of its own. Anyone with the URL can reach it — there is no login, signup, or session boundary at all today. This is a deliberate, temporary tradeoff made when Authentik was removed from the route, not an oversight, and it stays in place until NOW implements its own user accounts.

Authentik's boundary

What it protects, and what it deliberately does not

Authentik protects trusted internal and management applications. It does not, and will not, manage end-user identity for public applications like NOW. Those are two separate identity domains by design: Authentik groups (admins, trusted users, household members) are never substituted for an application's own user roles.

Admin tools today current

Komodo and Uptime Kuma are reached directly at a Tailscale IP and port, authenticating with their own native logins — not through Caddy, and not through Authentik.

Caddy + Authentik in front of admin tools planned — not implemented

Routing Komodo and Uptime Kuma through Caddy with Authentik forward-auth, matching the target architecture, is proposed only. It is not deployed. The original attempt hit a real limitation: Caddy cannot selectively restrict one of its sites to a single host IP under normal Docker bridge networking — host-IP-specific port publishing rewrites the destination to the container's internal address before Caddy ever sees which interface a connection arrived on, so a per-site bind directive can't tell "arrived via the Tailscale IP" from "arrived via the LAN IP." It briefly crash-looped Caddy in testing (bind: cannot assign requested address) before being reverted. If this is ever revisited, the two options on the table are network_mode: host for Caddy (which would give up the dedicated edge/auth/per-app network isolation model above) or a second, separate Caddy instance published only on the Tailscale IP. Neither has been judged worth it yet for two admin tools that already have their own login — direct IP:port access is simpler and just as private on a Tailscale-only path.

Checklist: adding a new application

Operational steps derived from the established patterns above
01
Repo layout — give it its own directory (an application stack alongside the other per-service directories in the IaC repo), not a subfolder of an unrelated stack.
02
Compose file — must run standalone with plain docker compose up -d over SSH. Never make it depend on Komodo to function.
03
Pin images, don't float — use a full version or immutable digest for new applications (caddy:2.11.4, not :latest). The current repository is mostly versioned but varies in tag precision, so tighten new stacks rather than copying a broad major-only tag. If building locally, pin the base image too.
04
Secret template first — ship an .env.example with variable names only, never real values. The real file stays local to the VM, outside Git, under a per-app secrets path. Anything that must be committed encrypted (as Komodo's database credentials are) goes through sops + age, decrypted only transiently at deploy time and never written to persistent disk in plaintext.
05
Persistent data placement — bind-mount application state under the per-app data path convention (as Authentik's Postgres does), or use a named Docker volume if the data doesn't need host-level visibility.
06
Healthcheck — define one if the upstream image supports it (Authentik's Postgres uses pg_isready). Not every current stack has one; treat it as the standard to write new stacks against, not a universal fact about what's deployed today.
07
Dedicated network — give the app its own Docker network shared only with Caddy, following the edge/auth/per-app model, rather than joining a shared default network.
08
No host ports by default — only publish a host port if there's a specific reason (the Tailscale-only admin-tool pattern is the accepted exception). Everything else should be reachable only via its dedicated network, through Caddy.
09
Caddy only if the app needs to be reached through the edge — pick one of the three patterns: Authentik forward-auth for a trusted internal tool without its own login, no forward-auth for a public app with native end-user auth, or no Caddy at all for a Tailscale-only admin tool.
10
Decide the route/domain up front — public (needs a real hostname and a Cloudflare Tunnel ingress rule), LAN-only internal hostname, or Tailscale-only IP:port. This decision drives which Caddy pattern applies.
11
Add it to monitoring — register an HTTP/TCP check in Uptime Kuma so an outage is visible instead of silent.
12
Backup/restore — confirm persistent data lives under the path covered by the VM-level PBS backup. Only add app-specific backup logic if the data genuinely can't be captured that way.
13
Validate before deploying — run docker compose config to catch interpolation and syntax errors before they hit a running host.
14
Deploy staged — bring it up manually via SSH + compose first, confirm it's healthy, before wiring it into Komodo for visibility or any future automation.
15
Know the rollback path — keep the previous known-good image tag noted so docker compose up -d with that tag is a one-line revert; fall back to a PBS restore only for whole-VM-level problems.
16
Update the docs — add the new routes/ports to the repo's route and port inventories and note any new Caddy pattern if one was introduced.

Current manual deployment

Every stack here is deployable by hand, over SSH
current

Caddy's admin API is fully disabled (admin off in the global block), not just left unbound, so the usual caddy reload live-reload path genuinely cannot work here. Any Caddyfile change needs docker restart caddy, which is a brief outage for every site Caddy fronts — plan config changes accordingly rather than expecting a zero-downtime reload.

env_file: inside the compose file alone is not enough here — Compose's own ${VAR} interpolation only reads a --env-file flag or a .env file next to the compose file, not the container-level env_file: directive. Both are used together deliberately.

Komodo's database credentials are committed to the repo only in encrypted form (sops + age). deploy.sh decrypts them to a memory-backed path using a root-only key kept outside Git, runs docker compose up -d, then removes the decrypted copy — plaintext credentials never touch persistent disk.

Releases & automated deployment

What exists today, and what's proposed

Today current

As of this snapshot (a point-in-time statement supplied for this page, not something pulled from the linked repository's own docs): NOW has no GitHub Actions workflow, no tagged releases, and no verified automated release-to-deployment pipeline. Getting a new build onto the VM today means the manual docker compose procedure above — there is no CI step, no image registry push, and no webhook in this loop right now.

  1. A tagged release triggers a GitHub Actions workflow that runs tests and builds the image
  2. The image is pushed to GHCR under an immutable tag or commit SHA — never a floating :latest
  3. Komodo picks up the new image via a webhook or resource sync
  4. Komodo drives a controlled docker compose redeploy on the Services VM
  5. A health check gates success; a known rollback path (previous pinned tag) exists if it fails

Komodo itself stays Tailscale-only in this proposal — none of this implies exposing Komodo's UI to the internet. If a webhook receiver is ever introduced so GitHub can notify Komodo of a new image, it would be a narrowly scoped, signature-verified receiver endpoint added deliberately behind Caddy — never the Komodo UI itself, and never an unauthenticated endpoint. None of this pipeline exists yet; it's a proposal to evaluate against the manual process above, not a plan with a committed timeline.

Operations & monitoring

Scheduled checks and firewall posture
current
Health check timerevery ~15 min · disk / containers / sites · notifies on state change only
Uptime monitoringUptime Kuma, Tailscale-only, HTTP(S)/TCP checks
Firewall defaultdeny incoming; SSH limited to the LAN and the Tailscale range; the Cloudflare Tunnel is outbound-only so it needs no inbound rule at all
Caddy admin APIadmin off — fully disabled, not just unbound
Docker bypasses UFW for published ports. Docker manipulates iptables directly for anything a container publishes, which sidesteps UFW's filter rules entirely. The real access control for Komodo, Uptime Kuma, and Caddy is which interface IP each is bound to (LAN vs. Tailscale), not a UFW rule — SSH is the one exception, since it's a non-Docker service genuinely governed by UFW.

Restoring this VM, fastest to slowest

01
Proxmox web UI — select VM 101 → Backup tab → pick a snapshot → Restore, in place or to a new VMID.
02
PBS web UI — browse a snapshot's file contents or restore individual files without touching the whole VM.
03
CLI, from the Proxmox host — list then restore:
# list backups for VM 101 pvesm list homelab-pbs --vmid 101 # restore in place qmrestore <backup-volid> 101 --storage local-lvm # or run an ad-hoc backup instead of waiting for 03:00 vzdump 101 --storage homelab-pbs --mode snapshot --compress zstd
04
Full hardware loss — only recoverable if the backup drive itself survived; requires rebuilding Proxmox and PBS on new hardware and re-registering the existing datastore rather than reformatting it.
Disaster recovery caveat: the backup datastore lives on one drive in the same machine it protects. That covers accidental deletion, bad deploys, and Proxmox-level mistakes — it does not cover that machine dying, being stolen, or a fire. Real disaster recovery requires periodically rotating the drive to a physically separate location; without that habit, this is backup, not DR, despite the software being called a Backup Server.

Known failure modes

Gotchas already hit once — don't re-discover them
01
Caddy config changes need a restart, not a reload. admin off means caddy reload has no admin API to talk to. Use docker restart caddy and expect a brief outage on every Caddy-fronted site.
02
Caddy can't bind one site to one host IP under normal bridge networking. Docker's port-publish rewrites the destination to the container's internal address before Caddy sees which host IP a request arrived on. A per-site bind directive doesn't achieve host-IP-based access control here — it previously crash-looped Caddy with bind: cannot assign requested address. This is why Tailscale-only admin tools publish directly instead of going through Caddy.
03
cloudflared needs an explicit TLS SNI override per ingress rule. Without setting the origin server name explicitly, cloudflared uses the internal service hostname (e.g. caddy) as the TLS SNI, which matches no site block in the Caddyfile and fails the handshake (tls: internal error, surfaced to visitors as a 502).
04
Caddy's internal CA regenerates if its data volume is recreated. Anything that pins Caddy's internal-TLS root certificate (like cloudflared's origin verification) needs re-extracting after that happens, or origin TLS verification will fail.
05
Query strings are logged verbatim. Caddy's access logging redacts Set-Cookie automatically but does not redact query parameters. No app behind this Caddyfile may put a secret in a query string.

Verification checklist

Run through this after any deploy or config change
01
Validate the compose file before applying anything: docker compose config.
02
Confirm containers are actually up and healthy: docker compose ps, then check any container-reported health status.
03
Tail logs for the affected service for obvious errors: docker logs <container>.
04
If Caddy config changed, confirm it actually restarted (admin off means no reload feedback loop to rely on) and check docker logs caddy for TLS or upstream errors.
05
Hit the route through its real path — through the tunnel for a public app, over Tailscale for an admin tool — not just container-to-container, to catch routing/DNS/TLS issues the internal check would miss.
06
Confirm the corresponding Uptime Kuma monitor reflects the change (new route added, or an existing one still green).
07
Update the route/port inventory docs if anything about the app's exposure changed.
