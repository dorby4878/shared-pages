Verification VM · VMID 103 · technical runbook

Every verification runs in its own throwaway container

dev-box is the isolated host where the Hermes agents verify application changes before a pull request: integration and end‑to‑end tests of an exact commit, several applications queued, each run in a fresh unprivileged container with its own Docker daemon and network — without touching the Agents VM, Hermes, the knowledge layer, or the Services VM's production workloads.

Source of truth / last verified: isolated backend installed and proven 2026‑09‑20; verification contract v2 (supervisor 2.0) deployed and accepted 2026‑09‑24. Contract source: homelab-stacks › dev-box/now-verify. Full internal runbook: homelab-stacks › docs/DEV-BOX.md. Day‑2 operations and incident handling are in the sections from Health checks onward. Treat conflicts in favor of re‑checking that repo and the live VM, not this page.

Architecture

A fixed protocol between an untrusted candidate and a root supervisor
current

The runner in the Hermes container never gets a shell on dev-box. Its SSH key is bound to a forced command that accepts only a small fixed set of validated operations; a root‑owned supervisor performs every privileged step and produces the evidence the verdict is computed from.

ComponentWhere / what
Supervisor now-verifydroot systemd service on dev-box; unix socket API; validates archives, drives Incus, enforces the global lock, tears every run down, then evaluates the host in three separate categories (security findings, cleanup findings, runtime observations) against a versioned policy and a pinned idle baseline
Client now-verifyctl + SSH gateunprivileged client; a forced‑command script maps the fixed operations to fixed client arguments (no shell, no forwarding)
Golden imageUbuntu 24.04 with Docker Engine and the Compose plugin, a non‑root candidate user; its fingerprint is pinned and checked before every run

Access architecture

Two paths in, both narrow by design
01
Admin (human) access — a personal key, same convention used for the other VMs on this host. Not used by any agent.
02
Hermes runner → verification gate — a dedicated ed25519 keypair generated inside the Hermes container's own persistent state directory (<per-agent state path>/.ssh/ — the same isolated, mode‑restricted location described in the Agents VM Runbook). Only the public half was installed on dev-box, in the runner account's authorized_keys with restrict and a forced command.

SSH alias (inside the Hermes container)

Host now-verify HostName <dev-box static LAN IP> User <runner account> IdentityFile <per-agent state path>/.ssh/<runner key> IdentitiesOnly yes UserKnownHostsFile <per-agent state path>/.ssh/known_hosts StrictHostKeyChecking yes

Host‑key verification is enforced, not skipped: the host key was captured from inside the Hermes container (the exact path Hermes uses) and cross‑checked against the key dev‑box itself presents before being trusted. Strict host‑key checking is asserted by the runner's own tests.

Gotcha: writing into the container's .ssh directory as the container's default (root) user creates root‑owned files that the unprivileged agent process cannot read. The symptom looks like a DNS failure (“could not resolve hostname”), not a permissions error. Always write as the agent's own user, or fix ownership afterwards.

Application contract

What a repository provides to be verified

The repository tracks a manifest naming one relative script — no arguments, no shell:

.prepr.json {"command": "./scripts/verify-prepr.sh"}

The exact commit is archived by the runner (never .git, never credentials), unpacked at /work/run inside a fresh container, and the script runs there with GIT_SHA, COMPOSE_PROJECT_NAME and CI=1. Defaults: 2 GiB / 2 CPU / 10 GiB disk / 30 min; the two heaviest applications get 3 GiB / 2 CPU / 12 GiB / 60 min. Anything the script needs (Compose, Playwright, databases) runs inside that container.

Health checks

Three commands, in this order
01
From the Hermes container (the real path): the health operation always answers; it must report the pinned supervisor version, worker_state ready, and exactly the nineteen frozen protected checks all ok. Any other state comes with an explicit reason code (busy, maintenance, recovering, quarantined + incident id).
02
On dev‑box: the admin evaluation must show no security and no cleanup findings (observations are fine) and no per‑run Incus instance may exist.
03
Service log: journalctl -u now-verifyd shows a clean start and no repeated “ADMIN ALERT” lines.

Use the durable job wrapper. A run can take up to an hour; a foreground terminal call is cut off after a few minutes. The job wrapper starts the verification detached, returns a job id at once, and is polled with a bounded wait; asking again for the same candidate returns the same job instead of a second run. If a connection or tool call is lost, the runner resolves that same run by its identity instead of killing it or running the candidate again. Only infrastructure failures that the supervisor itself classifies as retry‑eligible are retried (at most twice, fresh run id, identical archive); a failing test is never retried.

What a PASS means

Computed by trusted code from the supervisor's evidence

Two separate read‑only calls (status, evidence) are strictly parsed and compared with facts the runner computed itself from the exact archive it sent. Nothing the candidate printed, and not the SSH exit code, is an input.

Condition for PASSWhy
Pinned supervisor version and protocol; worker ready; exact frozen protected‑check names all okan unknown or changed supervisor, or a worker that is not ready, fails closed
Archive size, digest and manifest recomputed locally equal what the supervisor storedthe verified bytes are the sent bytes
Launch recorded with the exact expected command, resources, timeout and Compose projectthe run was configured as requested
Candidate exit code 0; no timeout, kill, refusal or errorthe script itself succeeded
Run container destroyed, no security findings, no cleanup findings, zero remaining processes, supervisor classification “passed”clean teardown; the record never claims the host was “unchanged”
Isolation attestation: nineteen protected checks, seven per‑instance checks, AppArmor label, ID map; the execution image and security‑policy generation seen at health timethe run really was contained, on the verifier that was checked

A lost connection never decides the result: the runner resolves the same run by its identity (status and evidence polling) and judges that run's own evidence; only if the run cannot be proven finished within its lifetime is it killed and cleaned — and a killed or recovered run never becomes a PASS. Infrastructure failures that the supervisor marks retry‑eligible (and the raw result confirms) are retried at most twice with a fresh run id and the identical archive; an application failure, timeout or kill is final.

The run journal

Durable record of runs that were accepted but not yet proven finished

Before a run may start, its id is written to a private journal directory in the runner's state area (mode 0700, owned by the agent user). The entry is removed only when a strictly parsed status that matches the run's identity (run id, commit, archive digest, and for the current run the manifest) shows it finished, or the supervisor states the run no longer exists. Every verification first reconciles the journal patiently: a listed run that may still be running legitimately is waited for (never killed early); only after its own lifetime has passed is it killed and cleaned. If the listed run was the identical candidate for the same purpose, its authoritative evidence is adopted instead of running the candidate again. A candidate is refused if any run cannot be proven finished. An entry that is malformed, foreign‑owned, world‑writable, or in an insecure directory also blocks.

Never delete a journal entry merely to unblock. First obtain an identity‑consistent terminal status (or the supervisor's “unknown run” answer) for that run id, or confirm on dev‑box that no Incus instance or project for that run exists and the supervisor is healthy. Only then delete that one file.

Changing the host

Maintenance window, then a reviewed per‑key baseline update
change control

Protected state (accounts, groups, Docker group, firewall, mounts, listeners, non‑run Incus objects) is compared with a pinned baseline. Ordinary Ubuntu background activity is not: it is classified against a versioned policy and verified against its package. An intentional change to protected state therefore needs a deliberate update.

01
Open a drained maintenance window (admissions pause, an active run finishes first) and make the change inside it.
02
Compare with the baseline: the only differing keys must be the ones you changed on purpose. Anything else is an incident, not a baseline update.
03
Update just those keys with the admin tool (it backs up the old baseline and logs the change and the reason).
04
Verify: health ready with all checks ok, admin evaluation clean, a fixture run passes.
Never re‑capture the whole baseline to silence an unexplained difference. Doing exactly that once adopted two orphaned network interfaces into the old baseline, which a later reboot exposed.
