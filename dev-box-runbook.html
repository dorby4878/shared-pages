Verification VM · VMID 103 · technical runbook

Every verification runs in its own throwaway container

dev-box is the isolated host where the Hermes agents verify application changes before a pull request: integration and end‑to‑end tests of an exact commit, several applications queued, each run in a fresh unprivileged container with its own Docker daemon and network — without touching the Agents VM, Hermes, the knowledge layer, or the Services VM's production workloads.

Source of truth / last verified: isolated backend installed and proven 2026‑09‑20. Full internal runbook: homelab-stacks › docs/DEV-BOX.md. Day‑2 operations and incident handling: Verification Backend Runbook. Treat conflicts in favor of re‑checking that repo and the live VM, not this page.

Architecture

A fixed protocol between an untrusted candidate and a root supervisor
current

The runner in the Hermes container never gets a shell on dev-box. Its SSH key is bound to a forced command that accepts only a small fixed set of validated operations; a root‑owned supervisor performs every privileged step and produces the evidence the verdict is computed from.

ComponentWhere / what
Supervisor now-verifydroot systemd service on dev-box; unix socket API; validates archives, drives Incus, enforces the global lock, tears every run down and diffs the host against its idle baseline
Client now-verifyctl + SSH gateunprivileged client; a forced‑command script maps the fixed operations to fixed client arguments (no shell, no forwarding)
Golden imageUbuntu 24.04 with Docker Engine and the Compose plugin, a non‑root candidate user; its fingerprint is pinned and checked before every run
Storage / networkdedicated btrfs pool, dedicated bridge, nftables + UFW rules tagged for this system
State & evidenceroot‑only state directory: per‑run state, evidence, logs, the idle host baseline

Access architecture

Two paths in, both narrow by design
01
Admin (human) access — a personal key, same convention used for the other VMs on this host. Not used by any agent.
02
Hermes runner → verification gate — a dedicated ed25519 keypair generated inside the Hermes container's own persistent state directory (<per-agent state path>/.ssh/ — the same isolated, mode‑restricted location described in the Agents VM Runbook). Only the public half was installed on dev-box, in the runner account's authorized_keys with restrict and a forced command.

SSH alias (inside the Hermes container)

Host now-verify HostName <dev-box static LAN IP> User <runner account> IdentityFile <per-agent state path>/.ssh/<runner key> IdentitiesOnly yes UserKnownHostsFile <per-agent state path>/.ssh/known_hosts StrictHostKeyChecking yes

Host‑key verification is enforced, not skipped: the host key was captured from inside the Hermes container (the exact path Hermes uses) and cross‑checked against the key dev‑box itself presents before being trusted. Strict host‑key checking is asserted by the runner's own tests.

Gotcha: writing into the container's .ssh directory as the container's default (root) user creates root‑owned files that the unprivileged agent process cannot read. The symptom looks like a DNS failure (“could not resolve hostname”), not a permissions error. Always write as the agent's own user, or fix ownership afterwards.

Application contract

What a repository provides to be verified

The repository tracks a manifest naming one relative script — no arguments, no shell:

.prepr.json {"command": "./scripts/verify-prepr.sh"}

The exact commit is archived by the runner (never .git, never credentials), unpacked at /work/run inside a fresh container, and the script runs there with GIT_SHA, COMPOSE_PROJECT_NAME and CI=1. Defaults: 2 GiB / 2 CPU / 10 GiB disk / 30 min; the two heaviest applications get 3 GiB / 2 CPU / 12 GiB / 60 min. Anything the script needs (Compose, Playwright, databases) runs inside that container.

Retired: direct‑Docker access

Why it was removed
removed 2026‑09‑20

The first version of this VM let the agent's SSH account run docker directly. Membership of the host docker group is equivalent to root on the VM, so candidate code could never be considered contained. That account was removed from the docker group once the isolated backend was live and proven; the old working directory and the direct path are unused and unreachable.

Change‑control consequence: host users, groups and the Docker group are part of the supervisor's idle baseline. Any intentional change to them makes the next run fail closed until the baseline is deliberately re‑captured — see the procedure in the Verification Backend Runbook.
