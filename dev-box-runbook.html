Sandbox VM · VMID 103 · technical runbook

A disposable box where an agent can break things on purpose

dev-box exists so the Claude Code instance running inside a Hermes container can provision, test, and destroy full application stacks — pre-PR verification — without ever touching the Agents VM, Hermes, the knowledge layer, or the Services VM's production workloads.

Source of truth / last verified: provisioned and end-to-end validated 2026‑09‑16. Full internal runbook: homelab-stacks › docs/DEV-BOX.md. Treat conflicts in favor of re-checking that repo and the live VM, not this page.

Purpose & architecture

One more hop, one more isolation boundary

Before this existed, there was no safe place for an agent to run docker compose up against arbitrary candidate code. dev-box is that place: a throwaway sandbox reachable only by the specific Hermes agent that needs it, with no path back into anything that matters.

Access architecture

Two separate SSH paths, by design
01
Admin (human) access — a personal key, same convention used for the other VMs on this host. Not used by any agent.
02
Hermes Claude Code → dev-box (the automated path) — a dedicated ed25519 keypair generated inside the Hermes container's own persistent state directory (<per-agent state path>/.ssh/ — the same isolated, mode‑restricted location described in the Agents VM Runbook's agent‑isolation model). The keypair never left the container; only its public half was installed on dev-box. Survives container restarts because that directory is bind‑mounted persistent storage, not container‑ephemeral.

SSH alias (inside the Hermes container)

Host dev-box HostName <dev-box static LAN IP> User claude-verifier IdentityFile <per-agent state path>/.ssh/dev-box_ed25519 IdentitiesOnly yes UserKnownHostsFile <per-agent state path>/.ssh/known_hosts StrictHostKeyChecking yes

Host‑key verification is enforced, not skipped: dev-box's host key was captured via ssh‑keyscan from inside the Hermes container (the exact path Hermes actually uses) and cross‑checked byte‑for‑byte against the key dev-box itself presents, before being trusted. StrictHostHostChecking no is never configured.

Gotcha hit and fixed during setup: writing into the container's .ssh directory as the container's default (root) user creates root‑owned files that the actual agent process — which runs as an unprivileged in‑container user — cannot read. The symptom looks like a DNS failure (“could not resolve hostname dev‑box”), not a permissions error, because SSH silently ignores a config file it can't open. Fix: always write as that unprivileged user, or chown the directory back to it afterward. Also noted in the Agents VM Runbook's failure modes.

Verification workspace

Every run is disposable; nothing here is a source of truth
/srv/prepr/runs/<repo>-<short-sha>-<run-id>/ # one dir per run /srv/prepr/artifacts/ # logs/screenshots worth keeping

Compose projects use -p prepr-<repo>-<shortsha>-<runid> so concurrent or successive runs never collide. Cleanup is docker compose -p <project> down -v from the run directory, then deleting the directory — no global Docker cleanup required, and unrelated resources are never touched.

Candidate source transfer

No GitHub credentials live on dev-box. The exact candidate commit is packaged and streamed over the same SSH connection already in use:

git archive <candidate-sha> | ssh dev-box 'mkdir -p <run-dir> && tar -x -C <run-dir>'

Temporary test secrets

Dropped into a single run directory with chmod 600, deleted on cleanup. Production .env files are never copied wholesale, and no production credential is ever written to this box.
