What a PASS means

Computed by trusted code from the supervisor's evidence

Two separate read‑only calls (status, evidence) are strictly parsed and compared with facts the runner computed itself from the exact archive it sent. Nothing the candidate printed, and not the SSH exit code, is an input.

Condition for PASSWhy
Pinned supervisor version and health; exact frozen check names all okan unknown or changed supervisor fails closed
Archive size, digest and manifest recomputed locally equal what the supervisor storedthe verified bytes are the sent bytes
Launch recorded with the exact expected command, resources, timeout and Compose projectthe run was configured as requested
Candidate exit code 0; no timeout, kill, refusal or errorthe script itself succeeded
Run container destroyed, host equals the idle baseline, zero remaining processesclean teardown
Isolation attestation: fourteen preflight and seven per‑instance checks, AppArmor label, ID mapthe run really was contained

Any transport failure is a FAIL. If a run was already accepted, the runner kills and cleans exactly that run and records what it could confirm; a recovered run never becomes a PASS.

The run journal

Durable record of runs that were accepted but not yet proven finished

Before a run may start, its id is written to a private journal directory in the runner's state area (mode 0700, owned by the agent user). The entry is removed only when a strictly parsed status that matches the run's identity (run id, commit, archive digest, and for the current run the manifest) shows it finished, or the supervisor states the run no longer exists. Every verification first reconciles the journal: it kills and cleans each listed run, and refuses to start a candidate if any run cannot be proven finished. An entry that is malformed, foreign‑owned, world‑writable, or in an insecure directory also blocks.

Never delete a journal entry merely to unblock. First obtain an identity‑consistent terminal status (or the supervisor's “unknown run” answer) for that run id, or confirm on dev‑box that no Incus instance or project for that run exists and the supervisor is healthy. Only then delete that one file.

Changing the host: the idle baseline

Users, groups and the Docker group are part of it
change control

After every run the supervisor compares the whole host with an idle baseline that includes the account, group and subordinate‑ID file hashes and the Docker group membership. An intentional change to any of those — for example removing an account from the Docker group — therefore makes the next run fail closed until the baseline is deliberately re‑captured. This happened once, for real, when the retired direct‑Docker account was removed.

01
Make sure no run is active and incus list --all-projects is empty.
02
Capture the current inventory and compare it with the baseline: the only differing keys must be the ones you changed on purpose. Anything else is an incident, not a baseline update.
03
Back up the baseline file, update just those keys, remove the fail‑closed marker, restart the supervisor.
04
Verify: health all ok, inventory identical to the new baseline, a fixture run passes.
Never re‑capture the baseline to silence an unexplained difference. The baseline is the reference the whole isolation claim rests on.
